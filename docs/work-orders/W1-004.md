# W1-004 — Checkout, Payment & Recourse + Autonomous-Store Primitives

Lane: Worker 1
Status: COMPLETE
Dependencies: W1-003 (merged @ 01f6bf3)

## Objective
Complete the commerce kernel's buyer-facing transactional surface: the full checkout → payment → recourse lifecycle as deterministic command/event flows, plus the autonomous-store primitives (the store-operational building blocks that Stage 4's autonomous runtime will compose).

## Scope
Under `packages/commerce` (module-system conforming), on top of the W1-003 twin + projections: end-to-end checkout completion (cart → checkout session → order with payment authorization, expiry/abandon handled as first-class states); payment processing as journal events — authorization, capture (partial + full), void, refund (partial + full, idempotent, currency-exact), each gated by policy and folded into the order/payment projections; the payment PORT extension for provider settlement outcomes (OBSERVED/UNKNOWN/FAILED tri-state preservation end-to-end — an UNKNOWN settlement NEVER becomes money-in); recourse primitives — dispute lifecycle (open/evidence/resolve), chargeback handling, goodwill vs policy refunds distinguished in the journal, recourse read models; autonomous-store primitives — the deterministic store-operation vocabulary (opening/closing counts, till operations, staff session handover as principal transitions, cash reconciliation events) that later stages compose into an autonomous runtime; every new flow expressed as commands + events with the twin-verification harness extended to cover them (twin ≡ kernel after arbitrary interleavings including failure + recourse paths).

## Truth distinctions
Money is integer minor units; settlement observations preserve tri-state (UNKNOWN stays UNKNOWN through every fold); recourse decisions are journaled policy applications, never silent mutations; the twin remains the derived mirror — divergence is a bug the harness must catch.

## Acceptance scenarios
1. Checkout journey: cart → checkout → order with authorized payment; abandon/expire paths reach terminal states deterministically; duplicate checkout submissions are idempotent.
2. Payment lifecycle: auth → capture (partial + full) → refund (partial + full, chained after capture only); void after capture is rejected as an invalid transition; every step is journal-observable and twin-projected.
3. Settlement tri-state: an UNKNOWN provider settlement outcome never promotes or drops money — the order/payment projections hold UNKNOWN until an OBSERVED outcome arrives or the recourse window closes.
4. Recourse: dispute open → evidence → resolve (accept/reject) flows are journaled; chargeback forces the refund path without double-refund; a goodwill refund and a policy refund are distinguishable in the journal and projections.
5. Refund abuse guard (commerce side): refund totals can never exceed captured totals for an order under any command interleaving (property test).
6. Autonomous-store primitives: opening count → till operations → handover → closing count → reconciliation events fold deterministically; a cash variance at close is an explicit journaled state, never an error swallowed.
7. Twin coverage: the twin-verification harness (fuzz vocabulary extended with the new command surface) holds twin ≡ kernel across all new flows including failure + recourse interleavings.

## Constraints
No floating-point money; no opportunity/organization/agent semantics (Worker 2 lane); no UI or connector concerns (Worker 3 lane); no provider integrations (settlement outcomes arrive via the existing payment PORT interface); no model/runtime authority; no production mocks; no scope beyond the commerce lane.
