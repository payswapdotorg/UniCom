**Owner:** Worker 1 — Product Home / Commerce Modules  
**Status:** READY_FOR_TL_DISPATCH

## Operator authority (2026-10-24, verbatim intent)

"We're building on zcode to use its best features for commerce, not to remove them like you have been doing. We need both zcode UI's best features and Unicom features to be apparent."

The UNiCOM side of "both apparent" = a commerce home that visibly carries the operator-approved command-center experience.

## Objective

Make the operator-approved UNiCOM Command Center the commerce host's HOME surface — the merchant-facing face of UNiCOM: morning brief, connected stores, missions, the Commander chat, the decisions queue, the watch ring, and skills. Port the approved design faithfully (it was reviewed and green-lit by the operator on 2026-10-23) into the commerce host's conventions, with deterministic demo data today and clean seams for the commerce backend (unicom-console) when it lands.

## The approved design (port source — clone and read it)

Reference repo: `https://github.com/payswapdotorg/unicom-console` (public):

- `src/components/product/*.tsx` — the 8 sections: command (morning brief), stores (connection hub + connect wizard), missions, chat (Commander), decisions (approval queue), watch (event ring), skills, heartbeat strip.
- `src/lib/product/data.ts` — the types and seed data (stores halcyon/mountain-reads/kaia, missions, decisions, watch events, skills, morning brief).
- `src/lib/product/store.ts` — the interaction model (sections, connect wizard steps, decision resolve, skill install, chat plan-tick).
- The visual language: warm ink/paper + emerald primary + amber decisions, dark-first control room. `README.md` documents the zcode→commerce feature mapping.

Port the EXPERIENCE (structure, flows, information density, states) — do not pixel-copy tailwind classes: this repo has its own design laws (DESIGN.md) and the commerce host's CSS conventions.

## Required behavior

1. The commerce host's Home surface IS the Command Center: the seven sections (Command brief, Stores, Missions, Commander, Decisions, Watch, Skills) with a section switcher matching the approved design (rail on desktop, bottom nav on narrow viewports), the always-visible heartbeat strip, and honest DEMO/connected state labeling (the host's EnvironmentBadge law).
2. Every journey family of the 19 (J19 discovery law) keeps a visible entry from the home surface and the Explore taxonomy — e.g. a labelled "Explore journeys" area/entry on the home surface. Nothing becomes deep-link-only. Roles/System surfaces stay reachable in the host nav.
3. Interactions port faithfully: the 3-step connect wizard (platform picker → credentials/name form → progress → connected store joins the ring with its fabricated initial catalog), decision approve/decline with the resolved list, skill install/uninstall per store, Commander chat with the plan-tick animation and evidence chips, mission lanes with progress.
4. Deterministic demo data = the approved seeds (same store identities, same flavor). No randomness without a seed; fixtures stay labelled as DEMO per host law.
5. Backend seams, ready but inert: a single module-level configuration — commerce API base URL from an env (e.g. `UNICOM_COMMERCE_API`, absent = demo mode) — and typed fetchers matching the contracts in `unicom-console/docs/BACKEND-ARCHITECTURE.md` (stores/decisions/missions/watch/skills/brief/commander routes), with graceful fallback to demo data on any failure. No network calls happen in demo mode.
6. DESIGN.md laws apply: `text-ui-*` type scale only, calm/dense/operational, light+dark themes, no marketing spacing, i18n-safe strings (follow the host's existing localization approach for new labels).
7. The host router/registry tests keep passing; new surfaces register through the existing module contract (no second drifting copy of the host).
