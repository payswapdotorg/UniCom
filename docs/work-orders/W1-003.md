# W1-003 — Commerce Twin + Event Projections

Lane: Worker 1
Status: COMPLETE
Dependencies: W1-002 (merged @ 81c64af)

## Objective
Build the Commerce Twin: deterministic event projections (read models) over the W1-002 kernel's append-only event journal, queryable without mutating the kernel, plus twin-state verification tooling.

## Scope
Under `packages/commerce` (module-system conforming), on top of the W1-002 runtime: projection infrastructure folding CommerceEvent streams into versioned read models; catalog, inventory, order, transfer, receiving, returns and reconciliation projections; the Commerce Twin — a full mirror of authoritative operational state derived ONLY from events (never from in-process kernel references), with a twin-verification harness that proves twin state ≡ kernel snapshot state after arbitrary command sequences; incremental projection updates with explicit ordering guarantees (per-aggregate sequence, no gap/torn reads); projection rebuild from empty journal reaching byte-identical state; snapshot-aware projection resume (rebuild from snapshot + tail replay); schema-versioned projections with explicit migration path (old events must project forward); demand-side projections exposing commerce facts (no opportunity semantics — those belong to Worker 2) for downstream lanes via typed, versioned query interfaces; tri-state preservation end-to-end (UNKNOWN projects to UNKNOWN, never silently promoted or dropped).

## Truth distinctions
Projections are derived state, never a second source of truth. Divergence between twin and kernel is a BUG, and the verification harness must detect it (property/fuzz cases, not just happy paths).

## Acceptance scenarios
1. Twin-verification harness: after randomized command sequences (including concurrent/conflicting and duplicate idempotent submissions), twin state equals kernel snapshot state exactly.
2. Full rebuild from an empty journal reproduces a live twin byte-identically (determinism, no wall-clock/environment dependence).
3. Snapshot-resume: rebuild from a mid-journal snapshot plus tail replay equals full rebuild.
4. Per-aggregate ordering: no projection observes effect B before its causal A under any interleaving the journal permits.
5. Schema migration: events written under projection schema N project correctly under schema N+1 via the explicit migration path.
6. UNKNOWN observations survive projection (an UNKNOWN inventory count projects to UNKNOWN in the inventory projection and the twin).

## Constraints
No floating-point money; no opportunity/organization/agent semantics (Worker 2 lane); no UI or connector concerns (Worker 3 lane); projections are read-only (a projection can never write back to the journal); no model/runtime authority; no production mocks; no scope beyond the commerce lane.
