## Objective

Turn the existing commerce host home from a reference/status index into a credible UNiCOM front door. A first-time buyer should immediately see a Buyer Intent Canvas; a merchant should immediately see a Command Center / Work Graph path. The UI must describe actual implemented capability honestly and expose the next useful action without requiring users to understand internal journey IDs.

Reuse the existing host, module registry, role model and public contracts. Do not restart the completed rendered-UI phase or replace it with static marketing pages.

## Required behavior

1. The ordinary UNiCOM home offers clear buyer and merchant/operator entry paths. The default emphasis respects the selected role; switching roles does not change identity or grant new authority.
2. Buyer entry uses the existing Intent Canvas and makes deadline, total-cost limit, quality, trust/privacy, delivery/pickup and acceptable substitutes understandable when supported by current types. Missing fields stay optional where the contract allows.
3. Merchant entry communicates current business state, active work/proposals, and high-value next actions using existing state and fixtures. It must not claim live order/inventory/connectivity facts that are not observed.
4. Existing journeys remain discoverable, but the full 19-row registry should not dominate the first screen as a raw implementation checklist. Keep Explore/capability discovery one click away.
5. Show the distinction between authoritative operational state, provider/physical observations and model predictions. Preserve UNKNOWN, stale, blocked, simulated and not-connected outcomes.
6. Every synthetic object/action remains visibly labelled DEMO/simulated. No live purchase, payment, group commitment, rental, swap or trade leg.
7. Use accessible headings, labels, keyboard/focus order, empty states and responsive layout. Continue using the established ZCode design tokens and frozen public contracts.
