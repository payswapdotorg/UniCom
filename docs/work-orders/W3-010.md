# W3-010 — Baseline Campaign Run (cycles.baseline): Real Artifacts, 3,900 Projects, Four Adoption Outputs

Lane: Worker 3 — Experience / Runner / Campaign execution
Status: READY
Dependencies: W1-009 (merged 47c07ce), W2-009 (merged 7bf1266), W3-009 (merged 2f1ff1f) — ALL LANES AT BASE. This is the first post-wave-009 work order: `cycles.baseline` in docs/development-state/v3-simulation-state.json.

## Objective
Execute the baseline campaign of the V3 simulation: run W3-009's GUI-only runner over W1-009's REAL portfolio and W2-009's REAL personas using the frozen adoption contract, producing the four adoption outputs and the machine-readable baseline report that the improvement cycles (protocol §7) and the release gate build on.

## Scope
1. Replace the local-dev fixture consumption with loaders for the real artifacts now at base:
   - W1 portfolio: `docs/simulations/scenarios/**` (manifest.json, industries.json, roles.json, journey-families.json, no-rfid-coverage.json, seed-namespaces.json) + the generator/oracle surface in `packages/commerce/src/test/w1-009/portfolio/**` (import, do not copy-fork; the commerce package is already a devDependency).
   - W2 personas: `docs/simulations/personas/cohort-manifest.json` (39 firms, 15,275 personas) + `adoption-contract.json` (frozen `w2-009:v1`) + the scoring engine exported from `@unicom/agent` (`computeAdoptionDecision`, `aggregateAdoption`, sensitivity helpers).
   - The local fixture stays ONLY as an explicit fallback for tests that must not depend on the full cohort; every campaign record must carry `localDevFixture: false` and the artifact ids it consumed.
   - The fixture's synthetic industry ids (retail-ecommerce, grocery-supermarket-no-rfid, ...) DO NOT match W1's real ids (construction, supermarkets-local-retail, ...). The loader maps to the REAL ids; the fixture vocabulary is retired from the campaign path.
2. Run the BASELINE seed namespace ONLY: exactly 3,900 projects (13 industries × 3 sizes × 100). The 3,900 holdout-namespace projects MUST NOT be executed, scheduled or scored in this work order (protocol §7 anti-overfitting). The scheduler must make this selectable and the campaign report must show `namespace: "baseline"` with zero holdout leakage.
3. For every project: schedule per campaign-config, execute the sampled journey families through the GUI-only runner, capture JourneyEvidenceRecords (unchanged W3-009 schema), apply the W1 oracle assertions AFTER the journey (never before), and record outcomes.
4. Score adoption per the frozen contract: map journey outcomes to per-persona `JourneyOutcomeForPersona`, run `computeAdoptionDecision` (veto-first) for each of the 15,275 personas, aggregate with `aggregateAdoption` per firm, per industry, per size, per role family, and overall.
5. Produce the FOUR adoption outputs exactly as defined in `adoption-contract.json` `fourAdoptionOutputs` (a: technical full-switch eligibility; b: simulated stated willingness to switch; c: main-interface eligibility; d: simulated stated willingness to use as main interface). Outputs b and d are booleans + scores; every willingness statement carries the `syntheticEstimateLabel` (protocol §8: "synthetic simulation estimate" qualifier is mandatory).
6. Write the machine-readable campaign report (full artifact + slim summary, mirroring the pilot pattern) plus the human-readable baseline report at `docs/simulations/campaign/BASELINE-REPORT.md` covering ALL §8 requirements: exact build/commit + timestamps, planned vs executed counts, firm/persona counts + cohort definitions, pass/fail/blocked/absent/unknown counts, industry × size × role results, UNiCOM vs incumbent evidence classes, the four adoption outputs with formulas/weights/thresholds/sensitivity ranges, journey evidence pointers, top friction causes with evidence, and limitations/confidence warnings.
7. Incumbent comparison stays commerce-only (the binding amendment): incumbent stacks are commerce tools/marketplaces/POS/procurement per the W2 cohort manifest; broad vertical software is excluded from performance claims and may appear only as evidence class C (capability checklist) or D — never as a measured competitor.
8. Reconciliation law: planned = executed + blocked + skipped for projects AND journey runs; blocked/skipped never leave the denominator. Zero-orphan map re-verified against the real portfolio (132/132 or better).
9. Determinism: identical inputs produce byte-identical campaign reports (excluding wall-clock timing fields, which must be isolated in the `throughput` block exactly like the pilot). Record build commit, seed namespace, and artifact fingerprints in the report.
10. Improvement-cycle staging (documentation only in this WO): the baseline report must end with a §7-cycle-1 readiness section — baseline failure list (if any), root-cause clusters (if any), and the untouched-holdout confirmation — but MUST NOT start cycle-1 fixes.

## Acceptance criteria
1. The campaign consumes the real W1/W2 artifacts (verifiable ids/fingerprints in the report); no synthetic fixture vocabulary appears in any campaign record.
2. Exactly 3,900 baseline-namespace projects execute; zero holdout-namespace projects run (asserted by test).
3. All 39 firms, 13 industries, 3 sizes, 15,275 personas appear in the aggregates; per-firm/per-industry/per-size/per-role breakdowns exist for all four adoption outputs.
4. The four adoption outputs are computed under the frozen `w2-009:v1` contract with zero changes to weights, thresholds, veto categories or formulas (contract file byte-identical at the end of the branch).
5. Every willingness number carries the synthetic-estimate qualifier; no unconditional "X% will switch" statement exists anywhere in the deliverables.
6. Project and journey reconciliation holds exactly (planned = executed + blocked + skipped; drift 0), including blocked/skipped in denominators.
7. Every project result and every failure carries a journey-evidence record pointer; the zero-orphan map passes for the real portfolio.
8. The baseline report covers every §8 reporting requirement (checked against the protocol list) and includes the sensitivity ranges from the W2 sensitivity helpers.
9. Re-running the campaign produces a byte-identical report modulo the isolated timing block (asserted by test on a sampled cohort; full-run determinism asserted by fingerprint).
10. The full verification battery passes: `pnpm -r --if-present test` (baseline at merge-base is 1,538/1,538 — the branch must end ≥ that with zero regressions), per-project typecheck for every file you touch, `pnpm lint` 0 errors, `pnpm architecture:check` 0 violations (max-file-lines 400 — split files proactively).
