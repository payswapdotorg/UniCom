## Objective

Convert the two most consequential demo-only commerce capabilities into kernel
truth: the **GroupBuy formation aggregate** and the **TradeCycle execution
aggregate**, inside `@unicom/commerce` — the runtime the web app is already
permitted to consume (`web → @unicom/commerce` via `contract.ts` only). This
is implementation within the frozen architecture baseline
`1.1-frozen-2026-10-05`: additive files inside the existing managed module
and its layers; the module graph, entrypoints and dependency directions are
unchanged.

## Scope A — GroupBuy formation aggregate

The aggregate that the final report records as absent ("no group-buy kernel
aggregate exists"). The rendered UIs on both sides (buyer `buyer-groupbuy`,
merchant `merchant-groupbuy-review`) currently keep formation outcomes in
local demo state; this aggregate becomes their canonical truth.

- Domain state machine (new files, deterministic, event-sourced like the
  existing aggregates): proposal PENDING → ACCEPTED (threshold MONITORING) /
  COUNTERED / REJECTED (with reason) / EXPIRED (window closed); participant
  interest recorded per participant with consent terms — **interest is never
  commitment**; withdraw permitted any time before the second confirmation;
  threshold-met pools HELD awaiting the organizer's explicit formation step;
  FORMED only on explicit formation with final terms (group price, pool
  value, participant roster of consenting-only participants); CLOSE/EXPIRE
  paths preserved.
- Handler commands (typed payloads, idempotent, journaled facts): open
  proposal, record interest, withdraw interest, merchant
  accept/counter/reject, form group buy, close/expire. Exact-money math only
  (`Money`, no floats); thresholds/quantities via the existing exact
  `Quantity` vocabulary.
- Kernel fold + snapshot projection for the new subjects.
- The J5 fixture scenario space (three consenting studios, excluded
  Northlight Atelier, Oct 20 pool close — see the W2-012/W3-015 fixtures)
  must be expressible as kernel scenarios in tests.

## Scope B — TradeCycle execution aggregate

The execution truth the agent lane's seam describes but the commerce kernel
does not yet own: multi-leg trade execution with per-leg authorization
references. The agent lane keeps discovery/proposals (unchanged, untouched);
THIS aggregate is the execution authority — candidates arrive as command
payloads with opaque item refs.

- Domain state machine: cycle OPEN with legs (each leg: pending → CONSENTED
  / REFUSED by its giving participant only, authorization references
  required); **ATOMIC mode**: any leg refusal → STOPPED_REFUSAL with **no
  leg committed**; all legs consented → COMMITTED. **STAGED_WITH_RECOURSE
  mode**: per-leg progression with per-leg recourse/rollback states.
  UNKNOWN-participant or ambiguous-authorization outcomes stay UNKNOWN —
  never silently passed, never collapsed into failures.
- Handler commands: open cycle (legs + mode + budget refs), authorize leg,
  refuse leg, execute, recourse actions (staged mode). Idempotency keys on
  every consequential command; immutable revisions; journaled facts.
- Kernel fold + snapshot projection.
- The J9 rendered scenario space (Cycle A refusal stops everything, "no
  other leg was committed") must be expressible as kernel scenarios.

## Interface and implementation rules

- Write ONLY inside `packages/commerce/src/**` (domain/, runtime/,
  projection/, test/) plus the additive `contract.ts` re-export block. No
  web, agent, experience, provider or shared edits. No package.json /
  lockfile edits. No new dependencies.
- Follow the kernel laws on the contract header: three-state truth; no float
  money; immutable ids/revisions; idempotency keys; UNKNOWN ≠ FAILED;
  provider-agnostic; typed commands are the only mutation path.
- `architecture:check` 0 violations; lint 0 errors (maxFileLines 400 with
  the test-tree exemption; split files mechanically, never disable rules);
  scoped typecheck clean. File-count discipline: new types in new files,
  re-exported from the one contract surface.
- Do not touch V3/post-V3/rendered-UI evidence or state records.
- Tests: exhaustive unit + kernel scenarios for both aggregates (state
  machines, refusal semantics, threshold holds, consent-only rosters,
  idempotent replays, UNKNOWN preservation).

## Acceptance criteria

- The seam commit is published first and referenced from the lane manifest.
- All batteries green on the lane branch; lane manifest documents every
