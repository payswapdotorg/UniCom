# W3-009 — GUI-Only Industry Simulation Runner and Instrumentation

Lane: Worker 3 — Experience / Connectors / Physical / Deployment
Status: READY
Dependencies: V3 simulation charter + current user-facing product; must consume W1/W2 contracts, not create new capability vocabulary

## Objective
Run user tasks through UNiCOM's actual GUI as an ordinary user would, at realistic multi-industry/firm scales, and capture reproducible evidence that distinguishes a genuinely discoverable feature from a backend-only implementation.

## Scope
- Build or extend a browser runner that starts from the public homepage/role landing view.
- Navigate using visible navigation, universal intent/command, onboarding or contextual opportunities.
- Use real clicks, keyboard/form controls and visible approvals. Do not satisfy a task via direct API/service/database/hidden-route actions.
- Capture screenshot checkpoints, accessibility/visible-control evidence, navigation graph, timings, interaction count, errors, backtracking, dead ends, retries and recovery.
- Integrate W1-009 deterministic project manifests and W2-009 personas/score schema.
- Run the 200-project-per-firm plan with deterministic browser session scheduling; record every scheduled, executed, blocked and skipped project.
- For first-time discoverability, forbid direct deep links to the feature under test.
- Support reset/bootstrap only as explicit preconditions; do not include setup time as task success or fake outcomes.
- Capture visible approval, evidence/proof and outcome summaries in the UI.
- Include multi-role switching and access-control tests.
- Include no-RFID supermarket GUI paths: POS/file import, barcode/camera count, weighted item, offline observation queue, receiving and reconciliation.
- Test offline/error/stale/UNKNOWN, missing connection, disabled permission, unsupported competitor and browser/session failure cases.
- Add zero-orphan tests: every feature-matrix row must map to discoverable surface plus an actual GUI journey or be marked FAIL/ABSENT.
- Keep deployment/testing isolated from production systems and provider accounts.

## Acceptance criteria
1. Starting from the homepage, an ordinary user can discover each tested feature; hidden-only paths fail.
2. UI evidence is captured and stored for every project result and every failure.
3. The runner never calls a product service or hidden route to complete an evaluated task.
4. Every scored interaction is a real browser user action against the deployed UI.
5. The runner consumes stable W1/W2 scenario ids and records build and seed identifiers.
6. It reports no data or fake competitor UI as if actually observed.
7. Unreachable UI paths, missing controls and permission blocks count as failed/blocked journeys, not passes.
8. At least one complete small, medium and large cohort runs end-to-end before launching the full 7,800-project experiment.
9. The full campaign counts reconcile: planned = executed + blocked + skipped; skipped/blocked never disappear from denominator.
10. Browser tests, instrumentation tests, typecheck, lint and architecture checks pass.

## Constraints
Do not add a parallel capability vocabulary or use direct internal methods as a workaround for poor UX. Do not run production purchases or mutate live accounts. Do not store credentials/screenshots containing sensitive values.

## Definition of complete
A GUI-only runner proves the required journeys through visible UI paths, captures evidence, and produces a machine-readable campaign report suitable for comparison and regression.
