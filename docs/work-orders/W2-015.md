## Required behavior (Stage 1, exactly)

1. **GroupBuy surface:** when a GroupBuy is FORMED (the aggregate state where formation truth exists), the acting merchant/organizer sees a clearly-labelled affordance: **"Create linked order draft"** (or the surface's established wording convention). Activating it is ALWAYS a separate human confirmation — it never fires on formation, never auto-runs.
2. **TradeCycle surface:** when a leg has EXECUTED (execution truth exists), the acting participant-side human with the appropriate role sees the same affordance for that leg only.
3. **Prefill, not a new command:** the affordance opens/redirects to the existing order-placement surface with the aggregate's facts pre-filled (items, quantities, and where the existing contract carries it, price terms), visibly marked as **pre-filled from the source aggregate** with the aggregate id rendered on-surface (provenance: which aggregate, which actor, which consent basis — all visible).
4. **The draft is a draft:** placing the order still requires the existing human confirmation flow unchanged (a draft is not a commitment; the existing place-order consent is the commitment step). The receipt/order references the source aggregate id where the existing typed contract allows carrying metadata today — if the existing command has no metadata field, render the reference on-surface instead and record that boundary honestly in the report; do NOT extend kernel contracts.
5. **Permission-aware:** the affordance renders only for actors whose role permits order placement in the existing role/permission model (mirror how existing order surfaces gate). A no-role/insufficient-role actor sees an honest unavailable state, not a silent absence — follow the established permission-block pattern from W2-014.
6. **Kill switch:** the affordance is behind a single local feature flag/module-level constant; disabled state = honest "linking disabled" label. Document it in the report.
7. **Demo labelling:** any synthetic prefill state stays DEMO-labelled per the repo's established on-surface convention ("synthetic demo state" etc.). No live commerce side effects of any kind.
8. **Payments/reservations/recourse: NOT in this lane.** If the prefill surface shows payment steps, they remain the existing demo/unavailable boundaries.
