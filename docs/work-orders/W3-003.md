# W3-003 — Canonical Connector Execution + First Provider Adapters

Lane: Worker 3
Status: READY
Dependencies: W3-002 (merged @ 29d0378); consumes W2-001 capability vocabulary + W2-002 kernel capability gates (merged)

## Objective
Execute real connector journeys on the W3-002 connector runtime: the first provider adapters, the LocalCommerceEdge, and the connector paths the handoff names — with canonical execution-mode coverage.

## Scope
Under `packages/experience` (module-system conforming), on the W3-002 runtime: first provider adapters for Shopify, eBay, Amazon, Jumia, Depop and Whatnot — each adapter implemented against the provider's real API semantics (auth flow, endpoint contracts, pagination, rate-limit/backoff behavior, error taxonomies) with provider-faithful recorded fixtures driving CI tests (fixtures are test doubles, clearly separated from adapter code — no production mocks); execution-mode coverage: at least one real adapter journey exercising each mode the provider permits — PASS_THROUGH_NATIVE, COMPOSED, OPTIMIZED_MULTI_PROVIDER (a journey = end-to-end observe→decide→execute against the adapter with evidence recorded); LocalCommerceEdge (local-first edge runtime: queueing, retry, reconciliation hooks to the commerce lane, degraded-mode operation); browser-only connector (a connector whose entire provider interaction runs through the W3-002 browser session runtime — no server-side provider credentials); live-commerce connector (live-event ingestion and execution over the runtime's live transport, Whatnot-class); feed/file connector (batch feed/file ingestion path with schema validation and partial-failure semantics); connector observability (per-adapter health, execution-mode telemetry, journey evidence records — building on the W3-002 health module); credential vault integration per adapter (vaulted at the connector boundary, never entering model context); capability-scoped adapter authority (adapters hold only the capabilities the W2 vocabulary grants — enforced by the W2-002 kernel gates, not convention).

## Truth distinctions
Provider observations arrive as OBSERVATIONS (tri-state), never promoted to authoritative commerce state by the connector; reconciliation stays an explicit commerce-lane operation. Adapter health is observability, not truth.

## Acceptance scenarios
1. Each of the six adapters passes its fixture-driven CI suite (auth, happy path, pagination, rate-limit backoff, error taxonomy).
2. Execution-mode journeys: at least one real adapter journey per mode (PASS_THROUGH_NATIVE / COMPOSED / OPTIMIZED_MULTI_PROVIDER) with recorded evidence; where a provider forbids a mode, the adapter blocks it explicitly (documented provider-permission matrix, not a silent gap).
3. LocalCommerceEdge: disconnected operation queues journeys; reconnect replays them exactly-once (idempotency keys survive restart); degraded mode never promotes observations.
4. Browser-only connector: provider interaction completes entirely inside the browser session runtime; server side sees no provider credentials (asserted by test).
5. Live-commerce connector: ingested live events execute in arrival order with backpressure handling; no event loss under burst fixtures.
6. Feed/file connector: malformed rows produce partial-failure reports with per-row dispositions; valid rows ingest exactly-once.
7. Observability: every journey emits an evidence record (adapter, mode, outcome, timing) queryable from the health surface.
8. Provider state preservation: adapters never mutate provider state outside the capability scope granted (W2-002 gate enforcement asserted).

## Constraints
No second capability vocabulary (consume Worker 2's); no canonical commerce truth (Worker 1 lane); credentials/PII never enter model context; no production mocks (fixtures are test doubles, separated); real-network journeys only where credentials are provisioned — fixture-driven CI is the merge gate, real-journey evidence lands with provisioned credentials and is tracked, not faked; no scope beyond the experience/connector lane.
