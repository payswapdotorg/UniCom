# W3-024 — Default Web + Ubuntu Desktop UNiCOM Launch Experience

**Phase:** Default UNiCOM Experience, tracking issue https://github.com/payswapdotorg/UniCom/issues/22  
**Owner:** Worker 3 — Experience / Connectors / Physical / Deployment  
**Status:** READY_FOR_TL_DISPATCH  
**Baseline to verify before dispatch:** main at or beyond 16bd4680073fed0a3c36ef61a39d270b95872d17  
**Depends on:** frozen architecture and current module host; W1-026 owns the commerce home/buyer/storefront UI; W2-029 owns autonomy/trust modules.

## Objective

The application itself—not a floating entry button—must open into UNiCOM. The browser root and packaged Ubuntu Electron app must start with the UNiCOM commerce experience and product navigation. ZCode remains the underlying agent operating kernel; its useful workspace should remain available through a deliberate secondary route if this is possible within the frozen architecture.

## Observed baseline / why this is separate work

- packages/web/src/commerceEntry.tsx explicitly calls the commerce host an add-on to the ordinary ZCode app and provides an overlay button.
- packages/web/index.html remains titled “ZCode”.
- packages/desktop/src/renderer/src/main.tsx currently initializes and renders the ZCode Root after desktop startup admission.
- packages/desktop/src/renderer/index.html still carries ZCode startup branding.
- packages/desktop/scripts/desktop-product-identity.mjs and packages/desktop/electron-builder.config.js define ZCode/ZCode Preview package identities and metadata.
- Local verification in the user's report showed the packaged ZCode-derived executable opens a 1200×800 window, but it does not prove the UNiCOM product UI was launched or that a DEB was installed.

- Desktop boot/render route and product-identity files under packages/desktop/src/renderer/**, packages/desktop/scripts/desktop-product-identity.mjs, packages/desktop/electron-builder.config.js, plus their focused tests/fixtures.

Do not edit packages/web/src/commerce-host/shell/CommerceHostApp.tsx, HomeSurface.tsx, W1-owned modules, W2-owned modules, package manifests/lockfiles or the architecture specifications. Coordinate any needed changes outside this write surface through the TL.

## Required behavior

1. Web route / renders the UNiCOM experience as the ordinary first landing. The floating “UNiCOM Commerce →” overlay must no longer be the main route to the product. Direct /commerce links continue to work compatibly.
2. Auth/OAuth callback and conversation-share routes keep their specialized behavior and are not accidentally redirected into the commerce host. Preserve safe return-target handling and all existing session/runtime boundaries.
3. The Ubuntu Electron app opens into a UNiCOM primary experience after required native startup admission and shows UNiCOM title/product identity/launcher identity consistently. Do not break startup failure/retry/exit, database readiness, message ports, task runtime, update windows, or remote workspace registration.
4. The product UI exposes a deliberate route into the retained ZCode agent/coding workspace where that can be achieved without violating current architecture rules. Do not remove or break the upstream runtime merely to hide its branding.
5. Use the same rendered commerce host and module contracts rather than creating a second independently drifting copy of the 19 journey families.
6. **Architecture gate before implementation:** read spec/architecture/FROZEN-ARCHITECTURE.md, spec/architecture/INVARIANTS.md, spec/dependency-graph.md, scripts/dependency-graph.mjs, and the current public package entrypoints. Do not introduce a desktop → web implementation dependency, a new public export or any dependency-graph edge unless it is already explicitly permitted. If no safe reuse path exists for desktop, finish the independent web default route, document a concrete option analysis and decision packet, and pause only the violating desktop seam for operator decision—never silently amend the frozen architecture or duplicate the entire host.
7. Replace remaining user-facing ZCode-first product identity with UNiCOM where it describes this product: browser title, desktop window/package/product metadata, launcher name/desktop entry and startup loading screen. Retain third-party notices and attribution. Keep test/preview suffixes unmistakable and maintain environment-vs-product identity separation.
8. Keep real commerce integrations disconnected. No credentials, network permissions, orders, payments, refunds, group-buy commitments or trade executions are part of this phase.

## Forbidden

- Making a new dependency/architecture edge look permitted by weakening the architecture checker or changing the frozen specs.
- Replacing commerce journeys with placeholders, disabling desktop startup safety, or removing the ZCode runtime.

- Claiming a packaged build is verified from a dev server, source-only build, window title alone, or a worker-written report without TL-observed evidence.
