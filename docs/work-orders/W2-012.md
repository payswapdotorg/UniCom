Phase: Rendered Commerce UI Implementation

Status: READY — operator approval required before implementation

## Objective

Implement rendered buyer-facing commerce journeys using the existing typed experience/runtime contracts. These are actual rendered screens with visible state transitions, not typed-only surfaces or fixture graphs presented as a UI.

## Owned journeys (protocol §10)

- J1 buyer intent and constraints: deadline, budget, quality, trust, delivery/pickup, substitutions, evidence and recourse.
- J2 sourcing and comparing offers across sellers; visibly distinguish verified, stale, UNKNOWN and unavailable information.
- J3 buy-now-vs-wait, price timing, negotiation and substitution.
- J4 discover/join an existing GroupBuy with threshold, deadline, eligibility, consent and commitment terms visible.
- J5 latent-demand GroupBuy buyer participation: recruit only consenting demo participants; propose merchant terms; show accept/reject/counter states. Coordinate contract boundaries with W3-015's merchant side.
- J6 rent/borrow vs buy: duration, availability, deposit, condition, return, damage and recourse.
- J7 resale/rental/consignment and user-controlled recovery of value from under-used assets.
- J8 proactive opportunities: price changes, warranty/recourse, subscription savings, loyalty, local pickup, shared logistics and future demand.
- J9 bounded multi-hop TradeCycle discovery, participant list, per-leg terms, per-leg consent, privacy/proof and recourse, including refusal/dropout.
- J14 Commerce Twin what-if/counterfactual UI; forecasts must be visibly non-authoritative and may not mutate canonical truth.
- The buyer-facing portions of J18 (stale results, UNKNOWN, approval denial, retries/recovery) with W3-015/W1 host shared state components.

## Interface and implementation rules

- Begin after W1-011 publishes a stable module contract. Implement only this work order's buyer/opportunity module directory and tests; do not edit the host router/shared shell.
- Use existing typed contracts and current business/runtime commands. If a required capability is only a contract with no working runtime behavior, label it as unavailable/demo-only and add a blocker; do not simulate a successful live outcome.
- Provide repeatable synthetic demo fixtures with separate namespaces and visible DEMO indicators. Do not send a real purchase, rental, group-buy commitment, refund, payment, or trade leg.
- Any state transition that represents commitment must show terms, consequence, evidence, and an explicit approval/confirm step. Demo confirmation may mutate only local test state.
- For TradeCycle, each leg requires separate consent; refusal, expiry or withdrawal must stop/re-plan the cycle without silently committing other legs.
- For GroupBuy, never treat expressed interest as a binding commitment. Show threshold, terms, deadline, and resulting states.
- Keep price, stock, quote and delivery source timestamps and freshness visible. UNKNOWN != FAILED and pending != settled.
- Ensure keyboard/screen-reader access and responsive layouts.

## Acceptance criteria

- Every owned journey has a visible UI entry reachable from ordinary navigation and every key state is observable.
- Buyer-side GroupBuy joins and latent-demand proposals show explicit authorization and counterpart/merchant response state.
- Renting/borrowing covers availability, duration, deposit, condition, return and recourse.
- Multi-hop TradeCycle demonstrates at least three synthetic participants and per-leg consent, including refusal/dropout and recovery.
- Proactive opportunities explain why suggested, evidence/provenance, expiry and safe next action.
- Commerce Twin clearly separates prediction from canonical state and cannot write commerce facts.
- Tests cover ordinary, empty, stale/UNKNOWN, denial, cancellation and recovery states—not only happy paths.
- Actual-browser evidence is captured once W1-011's rendered host exists; fixture tests are labelled separately.
- No UI-only claim substitutes for missing runtime capability. Any gap is added to the blocker register.

## Owned write surfaces

Own buyer/opportunity/peer-commerce screens, local UI state adapters and their tests in the agreed W2-012 module directory under packages/web. Do not change host routing/shared contract or merchant-owned screens.

## Deliverables

- Rendered buyer journey screens and module export conforming to W1-011.
- Unit/component tests and fixture-state manifest.
- Screenshots/traces plus a per-journey evidence matrix.
- Completion report with verified, demo-only, unavailable and blocked capabilities separated.
