# W1-010 — Rendered-Browser Commerce Journey Validation

Phase: Post-V3 Real-World Validation  
Lane: Worker 1 — Experience Plane / Browser E2E  
Status: READY  
Authority: docs/development-state/post-v3-validation-state.json  
Architecture baseline: 1.1-frozen-2026-10-05

## Objective

Turn the V3 fixture-level interaction graphs into genuine browser evidence from the rendered UNiCOM application, using a safe local or staging environment. V3 remains certified and immutable; this work is a separate validation phase.

## Scope

1. Inspect the repo and current environment to identify the supported application start command, reachable UI surface, browser/E2E tooling, seeded test data path, and safe local/staging URL. Record exact commit, environment, browser/version and prerequisites. Do not guess a deployed URL.
2. Launch a real browser and perform tasks from the ordinary homepage or role landing surface using visible clicks, typing, keyboard navigation and visible approvals. Do not score a task as passed through direct API/service/database calls, hidden routes, test helpers or synthetic success injection.
3. Cover all applicable items from the canonical 19-family journey registry in docs/simulations/V3-EXPERIMENT-PROTOCOL.md, including buyer intent, sourcing/comparison, negotiation/substitution, existing and latent-demand group buys, rent/borrow vs buy, resale/consignment, proactive opportunities, bounded multi-hop trades, merchant lifecycle, supplier procurement, autonomous-store approvals, Commerce Twin, connected channels/live commerce, local/physical commerce, no-RFID supermarket flows, trust/recourse and GUI discoverability.
4. Reuse the approved 13-industry / 39-firm scenario matrix as coverage input. Begin with a clearly labelled capacity pilot across small, medium and large profiles; do not call the pilot the full campaign.
5. Capture an evidence bundle for every attempted task: run ID, scenario/persona/role IDs, exact commit and environment, task steps, screenshot checkpoints (and trace/video where supported), visible route/navigation path, timing, retries/backtracking, outcome, failure reason, and evidence pointers. Redact tokens, cookies, personal data and secrets.
6. For first-discovery tasks, start at the ordinary landing surface and prohibit feature-specific deep links. A feature reachable only by deep link or not visible to the user is ABSENT for that journey.
7. Keep interaction evidence separate from backend verification. Backend checks may validate test setup or reconcile expected state, but cannot manufacture a GUI-pass result.

## Acceptance criteria

- The browser actually launches and renders the user-facing application; evidence identifies the application build and the tested URL/environment.
- The pilot contains reproducible, reviewer-openable browser evidence, not only deterministic interaction-graph fixtures.
- Each attempted journey reconciles as planned = executed + blocked + skipped with zero unexplained drift. Blocked, skipped, absent, UNKNOWN and failed outcomes remain visible in denominators.
- Journey discovery is demonstrably rooted at the homepage/ordinary role surface; no hidden-route-only capability is counted as present.
- Evidence covers applicable core commerce journeys across roles, including group buying, renting/borrowing, opportunity discovery and multi-hop trades with visible per-leg consent.
- Tests run only against an isolated local/test or explicitly approved staging environment; no production commerce writes occur.
- The TL can rerun the documented commands and reproduce the pilot report on the same build, or the report clearly explains why exact reproduction is environment-dependent.

## Out of scope / guardrails

- No production deployment or production mutation.
- No changing the frozen architecture or the V3 adoption contract.
- Do not represent a fixture-level success as actual browser validation.
- If no safe reachable GUI or browser runtime is available, record BLOCKED with evidence and the exact missing prerequisite. Do not synthesize screenshots, URLs or passing traces.

## Required deliverables

- Browser runner and tests in a clearly isolated experience-plane test surface.
- Machine-readable attempt/evidence manifest and human-readable pilot report.
- Screenshot/trace artifacts stored without secrets, with clear build and environment binding.
- Findings ranked by severity, affected journey family, reproducibility and user impact.
- TL handoff note stating exactly what was tested in a real browser versus what remains fixture-only.
