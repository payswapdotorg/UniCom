# W3-015 — Merchant, Procurement, Physical Commerce and Trust UI

Phase: Rendered Commerce UI Implementation  
Lane: Worker 3 — Merchant Operations / Procurement / Physical & Local Commerce / Trust  
Status: READY — operator approval required before implementation  
Issue: https://github.com/payswapdotorg/UniCom/issues/10  
State authority: docs/development-state/rendered-commerce-ui-state.json  
Dependency: W1-011 shared feature-module contract (first contract commit required)

## Objective

Implement the merchant/store/procurement and trust-side commerce experience as visible, rendered screens. Keep live integrations explicitly separate from local fixtures and show safe authorization and recourse behavior.

## Owned journeys (protocol §10)

- J10 merchant lifecycle: catalog/storefront, product and price management, promotions, inventory, checkout, orders, fulfillment/delivery, returns/exchanges/refunds/support.
- J11 supplier/procurement: discover suppliers, request/compare quotes, approvals, purchase orders, partial receiving, substitutions, receipt/invoice evidence and reconciliation.
- J12 B2B and multi-location/channel commerce.
- J13 autonomous-store rules, spend limits, approval gates, stop conditions and audit trail.
- J15 connected marketplaces, supplier portals, browser-only/file-feed/live-commerce connection status. Display what is genuinely connected versus demo/unavailable.
- J16 physical/local commerce and no-RFID supermarket: POS/CSV/barcode/camera/weighted goods, receiving, offline queue/replay, reconciliation, and explicit non-RFID capability.
- J17 trust, security, fraud prevention, wrong-item/counterfeit, review manipulation, return/refund abuse, disputes, evidence and recourse.
- Merchant-side J5 latent-demand group-buy proposal review, accept/reject/counter terms, and participant thresholds coordinated with W2-012.
- Merchant/supplier-side J18 stale providers, UNKNOWN/pending status, duplicate submission, missing approval, partial failure and recovery.
- Surface-specific support for J19 discoverability and role-appropriate navigation, without modifying the shared host router.

## Interface and implementation rules

- Begin after W1-011 publishes the shared feature-module contract. Own only the merchant/procurement/physical/trust module directory and tests. Do not change host routing or W2 buyer files.
- Reuse existing experience-plane view contracts and deterministic commerce runtime where available. If a provider/connector/runtime is not actually connected, expose a clear state and next step; never fabricate a successful integration.
- All demo flows use synthetic accounts, products, quotes, orders and vendors. Persistent local state must be resettable. No live purchase/payment/refund/order/rental or provider API side effect.
- Show distinct statuses for OFFERED, PENDING, ATTEMPTED, OVERDUE, SETTLEMENT UNKNOWN, NOT PROMOTED UNKNOWN, FAILED, DENIED and COMPLETED where the existing domain contracts define them; do not collapse non-failure states into errors.
- Display approval/authority boundaries before committing an action; denied actions need an accessible reason and safe recovery path.
- No-RFID workflows must not require an RFID identifier or device. Distinguish expected counts, scanned/measured counts, supplier receipts and reconciled results.
- Avoid broad comparisons against non-commerce vertical software. The product UI is commerce-specific.

## Acceptance criteria

- All owned journeys have rendered, discoverable views with navigation states tied to the W1-011 contract.
- Merchant GroupBuy review supports accept/reject/counter in local demo state and displays no binding effect.
- Orders, receiving, substitutions and reconciliation show provenance, quantity differences, approvals and recoverable exceptions.
- No-RFID inventory flow includes barcode/manual/weighted-goods count, offline queue/replay, conflict visibility and reconciliation.
- Trust/recourse flows expose evidence, decision status, policy reason, appeal/escalation and controlled refund/return actions.
- Autonomous-store controls expose bounds, approval gates, stop conditions and audit record.
- Integration manager differentiates connected, disconnected, demo and unavailable providers accurately.
- Tests cover allow/deny, duplicate request, stale/UNKNOWN and recovery cases.
- Actual-browser proof and screenshots are produced once the rendered host exists; unit/fixture pass alone is not browser acceptance.

## Owned write surfaces

Own merchant/store/procurement/physical/connection/trust modules and their tests under the agreed W3-015 directory in packages/web. Do not edit host/router/shared components or W2 buyer-owned modules.

## Deliverables

- Rendered merchant and operations modules conforming to W1-011.
- Component/integration tests and resettable demo seed data.
- Journey-to-screen discoverability map.
- Screenshot/trace evidence, blocker register and completion report.
