# W2-010 — GUI-Visible Resilience, Authority and Recourse Journeys

Phase: Post-V3 Real-World Validation  
Lane: Worker 2 — Commerce Truth / Trust / Security / Recovery  
Status: READY  
Authority: docs/development-state/post-v3-validation-state.json  
Architecture baseline: 1.1-frozen-2026-10-05

## Objective

Measure whether users can understand and recover from commerce failures through the actual UI. The V3 clean baseline and held-out run did not exercise the failure/UNKNOWN/recovery dimension; this work closes that evidence gap without touching production commerce state.

## Scope

Build a reproducible fault/scenario matrix in an isolated local/test environment, then use the real-browser runner and evidence format defined by W1-010. Inject faults only through controlled test adapters or fixtures; the user-visible task itself must still proceed through the UI.

Cover at least these scenario families where supported by the product:

- stale, slow, unavailable or contradictory connector/provider responses; UNKNOWN must not silently become FAILED or success;
- interrupted sessions, temporary network loss, retry and resumption;
- duplicate submit, retry-after-timeout and idempotency/reconciliation behavior;
- missing, denied, expired or revoked approvals/permissions;
- GroupBuy participant dropout, insufficient threshold, merchant counter-offer, expiry and cancellation;
- multi-hop TradeCycle of at least three participants, with each leg independently authorized; one participant refuses or withdraws consent, proof is incomplete, or recourse is needed;
- inventory changes, partial receiving, substitutions, delayed delivery, wrong item and reconciliation conflict;
- rental availability, deposit/condition evidence, late return, damage dispute and return/refund recourse;
- fake reviews/rings, counterfeit or item mismatch, false non-delivery claim, return/refund abuse and connector scope compromise;
- no-RFID supermarket offline queue/replay, barcode/camera/weighted-goods flow and reconciliation;
- autonomous-store guardrail trips and Commerce Twin forecast versus canonical commerce truth.

For each scenario define initial conditions, injected fault, expected state transitions, visible message, permitted action, blocked action, recovery path, evidence/proof requirements and terminal state. Include both expected-success and expected-block cases.

## Safety and authority invariants

- Security/authority policy blocks must be deterministic and visible.
- UNKNOWN is distinct from failure; pending payment or provider timeout must not be falsely represented as settled.
- No automatic purchase, refund, trade leg, rental commitment or external side effect without the configured explicit authority.
- A TradeCycle cannot execute any leg unless that leg has its own valid consent and authorization.
- Predictions and Commerce Twin counterfactuals never mutate canonical commerce truth.
- Repeated submissions must not create duplicate side effects.
- Use synthetic identities and isolated test fixtures only. Never send fault payloads or test transactions to live providers or production.

## Acceptance criteria

- Every fault variant has a stable scenario ID, deterministic setup, expected oracle, and result category.
- Every attempted task carries actual-browser evidence when W1-010 has made the runner available; fixture-only checks must be labelled as such.
- Every failure/recovery attempt reconciles its denominator, including blocked/skipped/UNKNOWN/aborted results; no silent drops.
- Tests prove both the allowed path and relevant deny/recovery path, not just that an error banner appeared.
- All critical authority, data-integrity and duplicate-side-effect invariants pass; any failure is a release-blocking finding until fixed or explicitly accepted by the operator.
- The TL can reproduce the report and map every result to a committed test, scenario and evidence record.

## Required deliverables

- Versioned resilience/fault matrix and expected-outcome oracle.
- UI-level tests and safe fault-injection adapters (if a required adapter is unavailable, document that gap rather than bypassing the UI).
- Machine-readable results, screenshots/traces and human-readable failure register.
- Severity-ranked remediation proposals. Do not alter architecture or loosen frozen security contracts to make a test pass.
