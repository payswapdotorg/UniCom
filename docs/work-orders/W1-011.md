# W1-011 — Rendered Commerce Host, Navigation and Shared UI Contract

Phase: Rendered Commerce UI Implementation  
Lane: Worker 1 — Host Integration / UI Platform  
Status: READY — operator approval required before implementation  
Issue: https://github.com/payswapdotorg/UniCom/issues/10  
State authority: docs/development-state/rendered-commerce-ui-state.json  
Architecture baseline: 1.1-frozen-2026-10-05

## Objective

Render UNiCOM's existing experience-plane surface contracts inside the reachable ZCode-based web application. Create the common shell, navigation, role switching and component contract so the buyer and merchant modules can be developed without overlapping files.

## Required initial inspection

- Read docs/FROZEN-ARCHITECTURE references and all 19 journey families in docs/simulations/V3-EXPERIMENT-PROTOCOL.md.
- Inspect packages/experience/src/surfaces/*.ts and existing runtime constructors before creating new models.
- Inspect packages/web, @zcode/ui patterns, current router/app entry and workspace dependency rules.
- Read docs/simulations/post-v3/FINAL-REPORT.md and preserve its exact finding: current commerce screens are not rendered.
- Record the selected host, routing and typed-contract mapping in a short design note before implementation.

If the only compliant implementation requires an architecture change outside frozen baseline 1.1, stop and present the smallest explicit decision request; do not silently amend the architecture.

## Scope

1. Implement a user-visible React commerce host in the existing browser application. Prefer consuming @zcode/ui and the current design-system conventions rather than duplicating a separate shell.
2. Connect the rendered host to existing typed view contracts/runtime constructors. Keep dependency direction valid under the frozen architecture; avoid adding React dependencies to domain/runtime-only packages unless already allowed.
3. Implement a clear navigation structure and ordinary homepage discovery for the 19 existing journey families; never rely on hidden-route-only access.
4. Provide a role switcher for at least buyer/requester, merchant/store operator, procurement/receiving, finance/approver and trust/support roles, while making permissions visible. One user may have multiple roles.
5. Provide responsive layouts, keyboard navigation, accessible names/focus states, useful empty/loading/error/UNKNOWN/offline states, and an always-visible environment/mode indicator.
6. Define and publish a stable feature-module contract for W2-012 and W3-015. Keep the host shell/router/role registry as this work order's owned write surface; feature workers own their module directories.
7. Add a local deterministic demo mode backed by committed synthetic fixtures. No real provider account or credential may be required to explore the core UI.
8. Make unavailable integration states explicit; do not label fixture data as live inventory, live quotes, actual merchant offers, or real transaction success.
9. Add route/surface inventory output that maps each of the 19 journey IDs to a visible nav entry or a documented role/contextual entry, with ordinary-discovery evidence.

## Acceptance criteria

- The browser shows rendered commerce pages, not the existing ZCode connect wall alone.
- The build uses real React components and renders at least one end-to-end journey module from each of W2-012 and W3-015.
- All 19 journey IDs have a human-readable visible entry point from normal navigation or an explicitly discoverable contextual entry. No direct deep-link shortcut may satisfy this criterion.
- The feature-module contract is type-safe and test-pinned. Feature workers can build independently against it.
- All clickable controls either work, are clearly disabled with a reason, or open an explanatory unavailable state; no deceptive dead buttons.
- At least one role with multiple permissions can switch roles without losing the scenario context, and unauthorized actions remain visibly blocked.
- Unit/component tests, typecheck, lint, architecture checks and actual-browser screenshots/traces are committed and reproducible.
- UI rendering never bypasses canonical commerce commands or safety/authority checks.
- Deterministic demo mode is clearly distinguished from connected/live mode.
- TL verifies merged-lineage evidence rather than accepting based only on worker claims.

## Owned write surfaces

Own host integration, router/navigation, role switcher, shared UI primitives/module contracts and host-level tests under packages/web. Do not implement buyer-specific or merchant-specific workflow logic except a minimal integration fixture.

## Forbidden

- Production deployment or live commerce mutations.
- Fabricated success, inventory, prices, supplier quotes, settlement or partner integrations.
- Changes to certified V3/post-V3 records or the frozen architecture without explicit separate authorization.
- Marking downstream journeys complete until W2-012/W3-015 screens are actually rendered and browser-verified.

## Deliverables

- Rendered host integration and role-aware navigation.
- Shared feature-module API/types.
- Route/surface discovery manifest.
- Host tests and browser evidence.
- Completion report with exact build/environment, screenshots, tests, limitations and merged commit.
