Trust ledger — four separate planes, never one score

UserTrust (who the counterparty is), AgentTrust (how reliable the agent worker is), Capability/ProviderTrust (how reliable a capability or provider implementation is) and TransactionProof (what actually proves a transaction) are four DIFFERENT planes. They are never compressed into a single score — the trust view contract has no score field — and a trust signal is never transaction proof. All values are committed demo fixtures w2-029-trust-planes@1 in the frozen field vocabulary.

AgentTrust — the Main Agent as a worker
AGENT_TRUST
DEMO

How reliable the agent is at what it does: task success rate and policy compliance. Agent trust is about the worker, never about money — it is not transaction finality and never will be.

Signal: Task success rate 0.94 (demo) · policy compliance CLEAN · assessed 2026-10-12 (demo clock) · evaluation lineage is an opaque ref in the frozen contract.

Risk: A non-compliant or low-success agent is a reliability risk for the work it prepares — not a payment risk.

Policy outcome: Gates what the agent may prepare (plans, comparisons, simulations). It never authorizes spending, never moves money, and never substitutes for an approval.

Evidence: Lab evaluation lineage (opaque evaluationEvidenceRefs in the frozen agent contract — not importable from the web plane; values labelled demo).

Mitigation / next step: On MINOR_VIOLATIONS the agent is demoted to supervised proposals; on SUSPENDED it stops acting entirely. Compliance is re-assessed on a fixed schedule.

TransactionProof — what actually proves a transaction
TRANSACTION_PROOF
DEMO

Proof is evidence-backed verification at a pinned level (P0–P5), selected BEFORE consequential execution. It is a distinct plane, constructible only from evidence — no trust signal can create, upgrade or stand in for it. A trust signal is never transaction proof.

Signal: On this surface: the kernel's journaled command receipts (EXECUTED with idempotency keys) are the P1-class facts; settlement observations carry provider-native statuses verbatim (P2-class when the rail signs).

Risk: Treating a trust signal (or an UNKNOWN settlement) as proof would invent money that was never verified — the exact failure the four-plane separation exists to prevent.

Policy outcome: Money-in derives ONLY from OBSERVED SETTLED; refunds are bounded by captured totals; UNKNOWN settlements stay UNKNOWN until observed or the window closes.

Evidence: The receipts, dispute records, chargebacks and settlement records on this surface — each journaled, each replayable in the audit trail below.

Mitigation / next step: When a fact matters, demand its level: check the receipt (P1), the provider-signed state (P2) or an independent observation (P3) — never a trust score, because none exists.

Proof legend — the only levels that exist
P0–P5

P0 — assertion: Stated without independent backing

P1 — receipt: Authenticated artifact or receipt

P2 — provider-signed: Provider-signed evidence

P3 — independent: Independent observation

P4 — protected: Corroboration plus economic protection

P5 — final: Native rail/ledger finality

Proof levels are selected BEFORE consequential execution and pinned to it. What proof is NOT: any trust signal. No UserTrust, AgentTrust or CapabilityTrust value can construct, upgrade or stand in for a TransactionProof — the planes stay separate on every surface.
